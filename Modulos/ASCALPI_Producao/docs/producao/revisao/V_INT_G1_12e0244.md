## 3. Achados

### INT-G1-01 — BLOQUEANTE de sincronização: SHA autorizado NÃO é fixado antes do pull

**Arquivo:** `Modulos/ASCALPI_Producao/Sincronizar_ASCALPI.cmd`, etapas 4 e 5.

**Como reproduzir sem modificar arquivos:** a implementação atual faz primeiro `git fetch`/`switch`/`pull --ff-only` e **depois** roda `git merge-base --is-ancestor "%PEDIDO%" HEAD`. Esse teste aceita **qualquer commit descendente** do SHA autorizado. Por exemplo, `7231955` é ancestral de `12e0244`; portanto, um `HEAD=12e0244` passa na validação com `PEDIDO=7231955`, embora contenha implementação adicional não coberta pelo aceite desse SHA. Pior: mesmo que o SHA não seja ancestral, o script apenas imprime `ATENCAO` **após ter alterado o código local**, sem reverter nem impedir o teste.

**Por que importa:** o Admin determinou fluxo **revisar nuvem → autorizar SHA exato → sincronizar clone → testar Windows**. O script atual pode testar código ainda não aprovado sob mensagem `SHA PEDIDO CONFERIDO`.

**Correção pedida:** buscar a referência remota, comparar **antes do checkout/pull** o commit efetivo de `origin/%BRANCH%` com o SHA aprovado (resolver SHA abreviado para commit completo). Se não for o mesmo, **abortar sem alterar o checkout**; não aceitar ancestral como equivalência. Após atualizar, confirmar `HEAD == SHA autorizado`; divergência deve resultar em falha explícita/não permitir continuação de testes. Se o usuário omitir SHA, mostrar exatamente o HEAD remoto e exigir aceite consciente do SHA antes de atualizar, ou exigir SHA para alterações. Restringir a sincronização padrão ao ramo de módulo aprovado, exceto autorização expressa do Admin.

**Regressão exigida:** reproduzir remotamente, sem tocar em `dados`, cenários: (a) `PEDIDO` ancestral mas diferente do HEAD remoto → **nega antes do pull**; (b) SHA ausente/não pertencente à branch → nega; (c) SHA remoto exato, checkout limpo e servidor fechado → avança e confere o resultado; (d) `git pull` falha → nunca anuncia sincronização bem-sucedida.
